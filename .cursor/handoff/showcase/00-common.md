# Showcase: общий бриф воркера

Ты — воркер эксперимента «Showcase». Цель — проверить **органику** кита Vuance UI
(`@pr0s1k/primetime-kit`): можно ли уже сейчас собрать на нём **красивое и адаптивное** приложение,
насколько это удобно и **каких кирпичиков (компонентов) не хватает**. Приложение — средство,
главный результат — честный отчёт `FINDINGS.md`.

## 1. Что прочитать (один раз, целиком)

1. `D:\dev\primetime\ui\kit\.cursor\handoff\showcase\kit-context.md` — всё о ките (~50k токенов).
   При сомнении смотри исходник `D:\dev\primetime\ui\kit\src\runtime\**`: исходник важнее файла.
2. Свой раздел в `D:\dev\primetime\ui\kit\.cursor\handoff\showcase\apps.md`.

## 2. Где работаешь

- Приложение: `D:\dev\primetime\ui\showcase\apps\<app>` (Nuxt 4, `app/` — srcDir).
  Уже есть: `nuxt.config.ts` (кит из локальных исходников `../kit/src/module.ts`, тема-сид),
  `app/app.vue` (`<m-app>`), заглушка `app/pages/index.vue` — замени.
- `nuxt.config.ts` можно менять (тема, шрифты `typography.fonts`, брейкпоинты, cookie): это тоже часть теста.
- Общие `node_modules` — в `D:\dev\primetime\ui\showcase`. **Новых зависимостей не ставишь.** Нужна —
  запиши находку «нужен пакет X для Y» и обойдись без него. `yup`/`zod` не установлены; для форм —
  контролируемые поля или адаптер кита `#kit/adapters/vee-validate` (если не резолвится — находка).
- Типы кита при локальных исходниках: `#kit/shared/types/props`, `#kit/components/ui/table/types` и т.д. (§1).
- Данные — статические моки в `app/data/*.ts` (реалистичные, 20–200 записей), состояние — `useState`/`ref`.
  Сети и серверного API нет.

## 3. Жёсткие правила

1. **Кит read-only.** В `D:\dev\primetime\ui\kit` ничего не правишь. Баг кита → обход в приложении + находка.
2. **Ни dev-сервера, ни сборки, ни браузера, ни Playwright сам не запускаешь.** Разрешено из
   `D:\dev\primetime\ui\showcase`: `npx nuxi prepare apps/<app>` и `npx nuxi typecheck apps/<app>`.
   Typecheck проверяет и исходники кита: ошибки в файлах кита не чинишь, только записываешь новые.
3. **QA — только через Haiku-агента, максимум 2 заявки на приложение** (третья — лишь если прошлая
   вернула «не компилируется / пустая страница»). Первая — когда готовы каркас и основные экраны,
   последняя — когда готово всё. Протокол — §6.
4. Никаких `git`-команд и коммитов.
5. Бюджет ограничен (весь эксперимент — 1.5 пятичасовых окна на всех). Не полируй бесконечно:
   находки важнее пиксель-перфекта. Ориентир объёма — в `apps.md`.

## 4. Как писать код

- Сначала кит: бери компонент кита везде, где он хоть как-то подходит, даже если неидеален, и записывай трение.
- `.vue`: `<template>` → `<script setup lang="ts">` → `<style lang="scss">`. Без точек с запятой.
- Свои блоки — BEM `<app>-<block>__<el>--<mod>` (`mail-thread__subject`). Каждому стилизуемому узлу — свой
  класс; без селекторов по тегам и без `>`; состояние — модификатор, не `data-*`.
- Размеры — только `rem` (= design px), цвета — только роли `--md-sys-color-*` с парой on-X, типографика —
  `@include typescale(...)` / `--md-sys-typescale-*`, углы — шкала формы, тени — `elevation()`. Прелюдия SCSS
  кита доступна в любом `<style lang="scss">` (§12).
- Перекрываешь стиль компонента кита классом родителя — составной селектор (§12, иначе ломается в prod).
- Файл ≤ 400 строк; компоненты — `app/components/**`, композаблы — `app/composables/**`.
  Комментарии — только «почему».
- Текст интерфейса — английский (кит пока без локали). Все `aria-label`/`messages`, у которых нет дефолта, — передавай.
- **Свои UI-компоненты** (то, чего нет в ките) клади в `app/components/custom/**`. Каждый такой компонент —
  обязательная строка в FINDINGS (§5). Если в течение работы ты сделал ≥ 3 кастомных компонентов —
  коротко сообщи менеджеру через SendMessage (`to` = id менеджера из `roster.md`; если его там нет — в финальном
  ответе): список и зачем.

## 5. `FINDINGS.md` (корень приложения, по-русски)

```md
# <App> — находки
## Итог (5–8 строк)
Удобство 1–5, красота 1–5 (самооценка по QA-скриншотам), сколько своего кода/CSS понадобилось, главные блокеры.
## Недостающие кирпичики
| Свой компонент | Файл | Почему кит не покрыл | Из чего собран (кит/композаблы) | Строк |
## Трение (DX)
- [high|med|low] компонент/проп — что мешало — как обошёл
## Баги кита
- компонент — шаги — ожидалось / получилось — обход — ссылка на исходник (если нашёл)
## Адаптив
- телефон / планшет / десктоп: что получилось, что нет (с учётом vw-масштаба 1rem = W/767|1199|1920)
## Что понравилось (оставить как есть)
```

Пиши находки **по ходу**, а не в конце: если контекст кончится, отчёт должен остаться.
Известные проблемы из §13 kit-context повторно не расписывай — пометь «подтверждаю §13 …» одной строкой.

## 6. Заявка в QA (Haiku)

1. Создай `D:\dev\primetime\ui\showcase\.qa\req\<app>-<N>.md`:
   ```md
   # REQ <app>-<N>
   from: <твоё имя из roster>
   app: <app>          # mail | store | tasks | finance | home
   routes: /, /inbox, /settings
   widths: 393,768,1024,1280,1920   # по умолчанию эти
   steps: .qa/req/<app>-<N>.steps.json   # необязательно
   look: 3–6 пунктов, на что посмотреть
   ```
   Шаги (необязательно) — JSON-массив `[{ "route": "/", "width": 393, "theme": "light", "steps": [
   { "click": ".mail-app-bar__menu" }, { "wait": 300 }, { "shot": "drawer-open" } ] }]`; действия:
   `click`, `fill`+`value`, `press`, `hover`, `wait`, `shot` (+`fullPage`). Селекторы — твои BEM-классы.
2. Найди id QA-агента в `D:\dev\primetime\ui\showcase\.qa\roster.md` и отправь
   `SendMessage(to: "<qa-id>", message: "REQ D:\dev\primetime\ui\showcase\.qa\req\<app>-<N>.md")`.
   (Если `SendMessage` не загружен — `ToolSearch` с `select:SendMessage`.)
3. Дальше либо делай другую работу, либо закончи ход строкой `WAITING QA <app>-<N>`. Ответ придёт
   сообщением `RES <путь>`: прочитай `.qa/res/<app>-<N>.md` и **сам посмотри скриншоты** (Read по PNG) —
   вердикт QA объективный (ошибки, переполнение), оценка красоты — твоя.

## 7. Готово, когда

- экраны из `apps.md` собраны (или осознанно урезаны — с записью почему);
- `nuxi typecheck` без ошибок в файлах приложения;
- последняя QA-заявка «OK» или оставшиеся «NOT OK» записаны в FINDINGS;
- `FINDINGS.md` заполнен.

Финальное сообщение менеджеру — **не больше 12 строк**: статус, путь к FINDINGS, 3 главные находки,
сколько своих компонентов. Длинные выкладки — только в файлах.
