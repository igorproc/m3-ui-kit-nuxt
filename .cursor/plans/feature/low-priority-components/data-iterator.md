Ценность появляется, когда нескольким коллекциям, кроме таблицы, нужен один и тот же конвейер: локальный фильтр, устойчивая сортировка, страницы. До финального API утвердить: только композабл или ещё и компонент, граница клиент/сервер (вопросы 1 и 2).</implementation-status>

## Вердикт

`нет в ките`. В M3 его нет, и он невизуален: это вторая половина системы кита — поведение
(`behavior.md`), а не форма. Прежнее направление остаётся: сначала **композабл**, компонент — только
если шаблонный DX со scoped-слотом окажется заметно лучше.

Главное, что выяснилось при сверке:
- **`MTable` уже управляемая.** Она рисует `data` как есть, отдаёт `v-model:sort` и
  `update:currentPage` и сама ничего не сортирует и не режет (`table/index.vue`). Итератор — это
  клиентский режим для неё и для любых карточек или списков, а не вторая таблица.
- **Страницы и виртуализация — альтернативы, а не слои.** `useVirtualScroll` принимает `count` и не
  знает, откуда элементы. Итератор без страниц отдаёт отфильтрованный и отсортированный массив,
  виртуализация рисует его окно. Друг друга они не импортируют.
- **Половина конвейера в ките уже есть:** `normalizePage`, `SortState<T>`, фильтр автокомплита.
  Новых сущностей нужно мало.

Отказы прежнего плана остаются:
- нет загрузки, кэша и серверного хранилища записей;
- нет разметки таблицы, списка или карточек;
- нет реестра выбора;
- нет Pinia-store;
- входной массив не мутируется;
- нет владения состояниями загрузки, ошибки и пустоты.

## Оси дизайна

Визуальных осей нет. Поведенческие:

| Ось | Значения | Комментарий |
|---|---|---|
| `mode` | `client \| server`, дефолт `client` | `mode` в ките — слово стратегии (`axes.md`). В `server` конвейер не режет данные, только держит запрос и правила сброса страницы (вопрос 2) |
| Сортировка | одна или несколько | массив `SortState<T>`; таблица отдаёт одну — её оборачиваем в массив |
| Страницы | `itemsPerPage > 0` или `0` | `0` — «все», для виртуализации |

## Оси состояний

| Ось | Нужно | Как |
|---|---|---|
| Пустой источник | `items = []`, `pageCount = 0`, `range = null` | владелец рисует `#empty` |
| Пусто после фильтра | отличимо от пустого источника | `totalItems = 0` при `sourceCount > 0` → «ничего не найдено» вместо «данных нет» |
| Страница вне диапазона | не бывает | `normalizePage` после каждого изменения длины |
| Смена фильтра, сортировки, размера страницы | страница сбрасывается | вопрос 3 |
| Смена источника (рефетч, удаление) | позиция сохраняется, если возможно | кламп, а не сброс (вопрос 3) |
| SSR | одинаковый порядок на сервере и клиенте | явная локаль сравнения (вопрос 4) |

## Поведение и доступность

- **Слои `behavior.md`.** Чистые функции (`filterItems`, `sortItems`, `paginate`) — без Vue и DOM.
  Над ними — `useDataIterator` на `computed`. Классов, `data-*` и бэгов атрибутов нет: это не
  control-композабл, у него нет DOM-части.
- **Неизменяемость.** Вход не мутируется: `toSorted` или копия перед сортировкой. Выход — новый
  массив только при изменении входа, запроса или страницы.
- **Устойчивость.** Сортировка стабильна: `Array.prototype.sort` стабилен с ES2019. Равные ключи
  сохраняют порядок источника; `null` и `undefined` всегда в конце, в обоих направлениях.
- **Объявления.** Число результатов и смену страницы объявляет постоянный `role="status"`
  владельца (у таблицы — DT-09). Итератор отдаёт только числа (`totalItems`, `range`) и текстов не
  строит: кит не поставляет непереводимых строк.
- **Фокус.** После смены страницы фокусом управляет владелец. Итератор DOM не трогает.
- **SSR.** Чистые вычисления без `onMounted`. Сравнение строк зависит от локали, поэтому локаль
  передаётся явно (вопрос 4).

## API

```ts
import type { SortState } from '#kit/components/ui/table/types'

export interface UseDataIteratorOptions<T extends { id: PropertyKey }> {
  items: MaybeRefOrGetter<readonly T[]>
  mode?: 'client' | 'server'                       // 'client'
  query?: Ref<string>
  filter?: (item: T, query: string) => boolean     // контракт useAutocomplete
  filterKeys?: readonly (keyof T)[]
  sort?: Ref<readonly SortState<T>[]>
  page?: Ref<number>                               // с 1, v-model MPagination
  itemsPerPage?: Ref<number>                       // 0 — без страниц
  totalItems?: MaybeRefOrGetter<number>            // только mode: 'server'
  locale?: MaybeRefOrGetter<string | undefined>
}

export interface UseDataIteratorReturn<T> {
  items: Readonly<ComputedRef<readonly T[]>>
  pageCount: Readonly<ComputedRef<number>>         // → MPagination :length
  totalItems: Readonly<ComputedRef<number>>
  sourceCount: Readonly<ComputedRef<number>>
  range: Readonly<ComputedRef<{ start: number, end: number } | null>>
}
```

Связка с таблицей и пагинацией (клиентский режим):

```vue
<MTable v-model:sort="tableSort" :data="iterator.items.value" … />
<MPagination v-model="page" :length="iterator.pageCount.value" />
```

Публичного компонента нет (вопрос 1). Возвращаемый тип объявлен явно: выведенные типы валят
`mkdist` с TS7056 (`behavior.md`).

## План работ (после продвижения)

1. **S — чистые функции**: `filterItems`, `sortItems` (устойчиво, `Intl.Collator`, `null` в конце),
   `paginate`; переиспользуют `normalizePage`.
2. **S — `useDataIterator`**: `computed`-конвейер, сброс и кламп страницы, метаданные.
3. **S — серверный режим** по вопросу 2: без нарезки, тот же сброс страницы, `totalItems` извне.
4. **S — рецепты в документации**: таблица в клиентском режиме; сетка карточек с пагинацией;
   длинный список с `useVirtualScroll` без страниц.
5. **S — подвал таблицы** берёт `range` для «1–5 из 42» (шаг 8 плана table), когда оба готовы.

## Тесты

- Unit (чистые функции): фильтр `contains` и свой; устойчивость сортировки на равных ключах;
  многоключевая сортировка; `null` в конце в обоих направлениях; числа в строках («файл 2» раньше
  «файл 10»); `paginate` на границах; вход не мутируется (`Object.freeze`).
- Unit (композабл): сброс страницы при смене запроса, сортировки и размера; кламп при укорочении
  источника; `server` не режет данные; одинаковый порядок при явной локали в SSR-рендере и на
  клиенте.
- Типы: `SortState<T>` таблицы принимается без приведения.

## Готово, когда

- [ ] Клиентский режим таблицы, сетка карточек и список с виртуализацией собраны из одного композабла.
- [ ] Вход не мутируется, сортировка устойчива, порядок одинаков на сервере и клиенте.
- [ ] Страница никогда не выходит за `pageCount`.
- [ ] Новых зависимостей и Pinia-store нет.

## Открытые вопросы

**1. Только композабл или ещё и renderless-компонент (вопрос прежнего плана)?**
1. Только `useDataIterator`. Всё поведение невизуально; разметка и слоты у потребителя.
2. Композабл + `MDataIterator` со scoped-слотом. Удобнее в шаблоне, но второй путь к тем же
   данным и лишний компонент в API.

Рекомендация: 1. Компонент — только если рецепты покажут, что шаблонный DX заметно лучше.

**2. Граница клиент/сервер.**
1. Один композабл с `mode: 'client' | 'server'`. В серверном он не режет данные, но держит
   запрос и **те же** правила сброса страницы — там и живут баги «страница 7 из 3».
2. Только клиент. Серверный режим каждый потребитель собирает из `useFetch` и своих `watch`.
3. Только запросное состояние для сервера, а клиентская нарезка — отдельный композабл. Два
   композабла с одинаковыми правилами страницы.

Рекомендация: 1.

**3. Что происходит со страницей при изменениях.**
1. Смена запроса, сортировки или размера страницы → страница 1. Смена источника (рефетч,
   удаление строки) → кламп через `normalizePage`, позиция сохраняется.
2. Всегда кламп. Пользователь остаётся на странице 4 после смены фильтра и видит не начало
   нового результата.
3. Всегда страница 1. Удаление строки на странице 4 выбрасывает пользователя в начало.

Рекомендация: 1. Это поведенческое правило, его подтверждает владелец.

**4. Локаль сравнения строк.**
1. Опция `locale`; без неё в деве — предупреждение при сортировке строк под SSR. `Intl.Collator`
   без локали берёт локаль среды, а она на сервере и в браузере разная: разный порядок и
   hydration mismatch.
2. Дефолт — `<html lang>`. Работает в браузере, но на сервере его надо достать из `useHead`, а это
   связь с приложением.
3. Сравнение по кодовым точкам без локали. Одинаково везде, но «ёж» встаёт после «яблока», а
   «файл 10» — перед «файл 2».

Рекомендация: 1.

**5. Готовый движок или свои утилиты (вопрос прежнего плана).**
1. Свои чистые функции, примерно 150 строк. Достаточно для фильтра, сортировки и страниц.
2. Headless-библиотека таблиц (например, TanStack Table core). Группировка, агрегаты,
   закрепление колонок из коробки, но это новая зависимость и вторая модель таблицы рядом с `MTable`.

Рекомендация: 1. К варианту 2 вернуться, когда появится заказчик группировки или агрегатов.
