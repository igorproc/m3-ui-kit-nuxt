# Validation API — расширенный `useField` и renderless `MValidation` для своих контролов (отложено до решения)

<implementation-status state="pending" updated="2026-10-07">Конвейер валидации в ките есть и работает через сменный адаптер; публичного `MValidation` нет. Отложено, потому что новый слой может оказаться фасадом без собственной ценности: сначала решить, хватает ли расширенного `useField`, и нужен ли своим контролам публичный renderless-компонент (вопрос 1). Условие продвижения: ответы на вопросы 1–6 и на общие вопросы фазы D Q12 (когда ошибка показывается впервые, FM-04) и Q13 (английские строки по умолчанию). Адаптер vee-validate и его экспорт `./validation` остаются — решение владельца 2026-10-06, не переоткрывается.</implementation-status>

## Вердикт

`нет в ките` — в части публичного API: `MValidation` нет, а `useField` отдаёт только
`errorMessage`, `hasError` и `meta`. Компонента нет и в M3: валидация — поведение, у которого
визуальной спеки нет (principles.md, «систем две»). Вид ошибки, ожидания и фокуса принадлежит
листовому полю и описан в его плане ([text-field](../components-should-update/inputs/text-field.md),
[dropdown](../components-should-update/inputs/dropdown.md) и др.).

Прежний план писался до рефакторинга адаптера, его схема устарела: `useFormSchema` больше не
строит Yup-схему, а `useField` не зовёт vee-validate напрямую. Решения прежнего плана
сохраняются:
- новая реализация переиспользует существующую систему;
- второй движок валидации, Pinia-store или параллельный контекст формы запрещены;
- `useValidation`, который лишь переименовывает `useField`, не создаётся;
- рекомендованное направление — расширенный `useField` для кита плюс тонкий публичный
  `MValidation` для своих контролов.

## Рендеры

Не применимо: это API без разметки. `MValidation` не создаёт DOM, композаблы не имеют SCSS.
Ошибка, ожидание, disabled и фокус рисуются полем — см. рендеры
[text-field](../renders/text-field/concept.webp) и
[form-renderer](../renders/form-renderer/concept.webp).

## Анатомия

Слои, а не части экрана. Сверено с кодом.

```text
provideValidationAdapter(adapter)            composables/validation/context.ts
    ↓ ValidationAdapter { bindField, createForm }   composables/validation/types.ts
useFormSchema → adapter.createForm            MFormRenderer
useField      → adapter.bindField(path)       MTextField, MCheckbox, MRadio(+group), MSwitch,
    ↓                                          MDropdown, MAutocomplete, MNumberInput …
поле: error / errorMessage → aria-invalid, aria-busy (meta.pending), строка поддержки
```

| # | Слой | Сейчас | Цель |
|---|---|---|---|
| 1 | Контракт `ValidationAdapter` | `bindField(path)` + `createForm`; `FieldBinding` = `value`, `errorMessage`, `meta` | новые члены — по вопросу 2 |
| 2 | Адаптер vee-validate (+ yup) | `adapters/vee-validate/` (`index`, `schema`, `useFormBuilder`), экспорт `./validation` | остаётся; реализует новые члены |
| 3 | `useField` | путь читается один раз в setup; без пути или без адаптера поле инертно | расширенный возврат (раздел API) |
| 4 | `MValidation` | нет | renderless-обёртка над `useField` с типизированным слотом (вопрос 1) |
| 5 | Поле | ошибка: поле → проп `errorMessage` → `helperText` (`useTextField`) | без изменений; читает `shouldShowErrors` |

## Оси дизайна

Визуальных осей нет. Поведенческие (behavior.md):

| Ось | Кандидат | Решается |
|---|---|---|
| Когда валидировать | `validateOn: ('input' \| 'change' \| 'blur' \| 'submit')[]` | значения по умолчанию — общий Q12 |
| Когда показывать ошибку | `showErrorsOn: ('dirty' \| 'touched' \| 'validated' \| 'submit' \| 'always')[]` | общий Q12 |
| Форма или одиночное поле | путь в контексте формы · без формы | вопрос 3 |
| Внешние (серверные) ошибки | `externalErrors: string[]` | вопрос 6 |

Прежнее предложение для Q12 передаётся туда как вариант, а здесь не решается:
`validateOn: ['blur', 'change']`, `showErrorsOn: ['touched', 'submit']`; нетронутое поле ошибку
не показывает; после первой неудачной проверки ввод перепроверяется сразу, чтобы ошибка ушла,
как только значение исправлено; отправка показывает все ошибки.

## Оси состояний

| Ось | Нужно | Есть | Не хватает |
|---|---|---|---|
| Валидность | valid / invalid, несколько ошибок | одна строка `errorMessage`, `meta.valid` | `errors: string[]` |
| Показ | ошибка видна только по политике | показывается сразу, как пришла от адаптера (FM-04) | `shouldShowErrors` (Q12) |
| Касание | dirty, touched, validated | в `meta` | `setTouched`, `reset` |
| Асинхронность | pending | `meta.pending` → `aria-busy` у полей | — |
| Внешние ошибки | серверные отдельно от клиентских | только проп `errorMessage` у поля | `externalErrors` + контракт очистки (вопрос 6) |
| Ручное управление | validate, reset, setErrors | нет | новые члены контракта (вопрос 2) |

## Токены

Не применимо: у renderless- и composable-слоёв нет SCSS. Токены ошибки, ожидания, disabled и
фокуса принадлежат визуальному полю, и `MValidation` их не выбирает.

## Поведение и доступность

- `aria-invalid` ставится только при видимой ошибке (`shouldShowErrors`), а не по факту скрытой
  ошибки — это уже принятое решение Q8 фазы D, у полей оно работает.
- Асинхронная проверка сообщает `aria-busy` (у полей уже по `meta.pending`).
- Сообщения связываются с контролом стабильными `id` и `aria-describedby` на уровне визуального
  поля. Для своего контрола `MValidation` отдаёт в слот `messageId` (через `useId`), а связь
  ставит потребитель.
- SSR: при первом рендере ошибки не показываются; `id` детерминированы.
- Слушатели и наблюдатели снимаются со scope; путь не перерегистрируется молча (вопрос 5).
- Сообщения правил по умолчанию — строки для пользователя: кто их поставляет и на каком языке —
  общий Q13 (CT-13), здесь не решается.

## API

Кандидат из прежнего плана, сверенный с кодом. Возврат расширяется, существующие поля
(`errorMessage`, `hasError`, `meta`) остаются — потребители кита не ломаются.

```ts
interface UseFieldOptions<T> {
  path?: string                              // как сейчас: читается один раз (вопрос 5)
  model: Ref<T>
  rules?: FieldRules                         // одиночное поле (вопросы 3 и 4)
  externalErrors?: MaybeRefOrGetter<string[]>
  validateOn?: ValidationTrigger[]           // дефолты — Q12
  showErrorsOn?: ErrorDisplayTrigger[]       // дефолты — Q12
}

interface UseFieldReturn<T> {
  errorMessage: Readonly<Ref<string | undefined>>   // есть
  hasError: ComputedRef<boolean>                    // есть
  meta: FieldMeta<T>                                // есть
  errors: Readonly<ComputedRef<string[]>>
  shouldShowErrors: Readonly<ComputedRef<boolean>>
  validate: () => Promise<FieldValidationResult>
  reset: (value?: T) => void
  setTouched: (touched?: boolean) => void
  setErrors: (errors: string[]) => void
  onInput: () => void
  onChange: () => void
  onBlur: () => void
}
```

`MValidation` (вариант B прежнего плана, вопрос 1):

```vue
<MValidation v-model="rating" path="rating">
  <template #default="field">
    <CustomRating
      :model-value="field.value"
      :invalid="field.shouldShowErrors"
      :aria-describedby="field.messageId"
      @update:model-value="field.setValue"
      @blur="field.onBlur"
    />
    <p v-if="field.shouldShowErrors" :id="field.messageId">{{ field.errors[0] }}</p>
  </template>
</MValidation>
```

Слот отдаёт возврат `useField` плюс `value`, `setValue` и `messageId`. Пропы: `modelValue`, `path` (имя пути — как у полей кита, в прежнем плане было `name`),
`rules`, `externalErrors`, `validateOn`, `showErrorsOn`, `disabled`, `readonly`. Событие
`clear:external-errors` — по вопросу 6. Компонента `MMessages` из прежнего примера в ките нет:
строку поддержки рисует поле; для своего контрола — предложение UX 4.

## Тесты

- Unit `useField` с фейковым адаптером без движка: инертность без пути и без адаптера; триггеры
  и показ по Q12; `errors[]`; `reset` и `setTouched`; внешние ошибки и их очистка.
- Контрактные тесты адаптера vee-validate на те же сценарии — без записи куда-либо, только
  поведение.
- `MValidation`: не рендерит своих элементов (`wrapper.html()` равен слоту); типы слота
  выводятся; `aria-invalid` у примера только при видимой ошибке (Q8).
- e2e на фикстуре формы: первый показ ошибки по Q12; `aria-busy` при асинхронной проверке; axe.

## Предложения по UX

Сверх базового объёма; решает владелец. Без новых зависимостей. Сводка ошибок после отправки
уже есть в плане [form-renderer](../components-should-update/form/form-renderer.md) (FM-11) и
здесь не повторяется.

| Предложение | Что получает пользователь | Заказчик | Цена | Рекомендация |
|---|---|---|---|---|
| Ошибки сервера на поля: `form.setErrors({ path: string[] })` для ответа 422 | Ошибка «email уже занят» появляется у поля, а не тостом | любые формы с серверной проверкой | S · метод формы поверх контракта вопроса 6 | да |
| Задержка асинхронных правил (`debounce`) и отмена устаревшего результата | Проверка «логин свободен» не дёргается на каждую букву и не показывает ответ на старое значение | регистрация, промокоды | S · опция `useField` | да |
| Фокус на первое невалидное поле после неудачной отправки (если сводки нет) | Не нужно искать ошибку глазами на длинной форме | длинные формы без `MFormRenderer` | S · опция формы | да |
| Публичная строка поддержки (`MFieldSupport`): текст, иконка ошибки, зарезервированная высота | Свой контрол выглядит как поле кита и не прыгает при ошибке | рейтинги, свои пикеры | S · вынести существующую часть поля, токены те же | обсудить |

## Открытые вопросы

Политика первого показа ошибки (Q12, FM-04) и английские строки по умолчанию (Q13, CT-13) —
общие вопросы фазы D, здесь не дублируются.

**1. Нужен ли публичный `MValidation`?** (прежний пункт 1)
1. Только расширенный `useField`. Минимум публичной поверхности, но свой контрол в шаблоне
   требует setup и ref.
2. `useField` + тонкий renderless `MValidation` поверх него (вариант B). Шаблонный путь для
   своих контролов и движок скрыт, но это ещё одна публичная сущность.
3. Публичная директива `v-validation`. Нет обёртки, но директива не умеет вернуть реактивное
   состояние в шаблон.

Рекомендация: 2 — прежнее рекомендованное направление.

**2. Новые члены контракта адаптера — обязательные или необязательные?**
1. Необязательные: кит проверяет наличие и даёт запасное поведение (например, `reset` через
   запись `initialValue`). Свои адаптеры не ломаются, но в ките появляются ветки.
2. Обязательные: контракт честный и короткий, но каждый свой адаптер ломается при обновлении
   (версия alpha это разрешает).
3. Отдельный расширенный интерфейс (`ValidationAdapterV2`) рядом со старым. Ничего не ломает,
   но два контракта надо поддерживать.

Рекомендация: 1. Контракт задуман так, чтобы пользователь писал адаптер сам.

**3. Одиночное поле без формы.** (прежний пункт 3)
1. Через адаптер: `bindField` получает `rules` и создаёт локальное поле вне формы. Один движок,
   но адаптеру нужен ещё один режим.
2. Маленький исполнитель `FieldRules` внутри кита без адаптера. Работает без зависимостей, но
   это второй движок — прежний план его запретил.
3. Не поддерживать: без пути поле инертно, потребитель проверяет сам и передаёт `errorMessage`.
   Ноль кода, но свой контрол без формы остаётся без помощи.

Рекомендация: 1.

**4. Форма правил.** (прежний пункт 3, тип `ValidationRule<T>`)
1. Декларативные `FieldRules` (`required`, `min`, `max`, `email`, `pattern`) — уже в контракте и
   переводятся любым адаптером. Сериализуемы, но кастомное правило не выразить.
2. Функции `ValidationRule<T> = (value: T) => true | string | Promise<…>`, как в прежнем плане.
   Выразительно, но адаптер с декларативной схемой их не переварит.
3. Оба: `FieldRules` плюс `custom?: ValidationRule<T>[]`. Покрывает всё, но два пути.

Рекомендация: 3, функции только как дополнение.

**5. Реактивный путь.** (прежний пункт 4)
1. Путь читается один раз в setup, как сейчас; смена пути в деве даёт предупреждение. Просто и
   уже задокументировано в `useField`.
2. Реактивный путь с безопасной перерегистрацией поля. Нужен динамическим формам, но это
   жизненный цикл регистрации в каждом адаптере.

Рекомендация: 1. Динамические формы ([form-renderer](../components-should-update/form/form-renderer.md),
шаг 2) монтируют и снимают поля, а не меняют путь у живого.

**6. Очистка внешних ошибок.** (прежний пункт 5)
1. Обёртка не меняет входной проп, а при изменении значения эмитит `clear:external-errors`;
   когда убрать устаревшую серверную ошибку, решает потребитель (прежнее предложение).
2. Кит сам прячет внешнюю ошибку после изменения значения, пока проп не обновится. Удобно, но
   показ расходится с данными потребителя.
3. Ничего не делать: ошибка висит, пока потребитель её не уберёт. Просто, но исправленное поле
   продолжает кричать.

Рекомендация: 1.
