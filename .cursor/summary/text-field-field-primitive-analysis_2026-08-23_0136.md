# text-field — анализ «большого топика» (field-примитив)

**Дата:** 2026-08-23
**Статус:** только анализ, код `text-field` НЕ менялся. Ждём выбора цели/`погнали`.

---

## TL;DR

`text-field` ощущается «большим и ни о чём», потому что это **не компонент, а тонкий
конфигуратор общего примитива `Field`**. Вся вёрстка и стили живут в общем фрагменте
`fragments/field/root.vue` (461 строка), а общие токены и пропсы **мисноминированы** —
лежат под именем `text-field`, хотя используются целым семейством полей.

---

## Карта: где что лежит

| Файл | Строк | Что внутри |
|---|---|---|
| `components/ui/text-field/index.vue` | 77 | проводка `<input>` ↔ `FieldRoot`, ARIA, `useTextField`. **Стилей нет.** |
| `components/ui/text-field/props.ts` | 50 | пропсы text-field + **общий** `mFieldProps` (тут же, не в field) |
| `composables/text-field/useTextField.ts` | 98 | логика: `useField` (валидация), focus, error-precedence |
| `components/fragments/field/root.vue` | **461** | **вся вёрстка + ~300 строк SCSS** (filled/outlined/plain × 5 состояний) |
| `assets/stylesheet/components/text-field/_index.scss` | 151 | токен-карта (префикс `m-text-field`) |

## Радиус поражения (это НЕ изолированный компонент)

- `FieldRoot` (`fragments/field/root`) импортят: **text-field, number-input, textarea**.
- Токены `components/text-field` `@use`ит: только `FieldRoot` → фактически это **общая
  field-карта**, просто названа `text-field`.
- `mFieldProps` используют: **autocomplete, file-input, number-input, text-field, textarea**.
- `dropdown` стилизует `:deep(.ui-text-field__control)` (композитный multiple-режим).

## Находки

1. **Мисномер / спутанное владение (корень проблемы).** Универсальный примитив `field`
   (класс `ui-field`, `mFieldProps`, токен-карта) замаскирован под конкретный `text-field`.
   Общее и специфичное не разделены.
2. **`FieldRoot` — god-file 461 строка** (> лимита 400): шаблон + вычисление классов +
   ~300 строк SCSS в одном файле.
3. **Двойная эмиссия классов оправдана — НЕ трогать вслепую.** Каждый элемент получает
   `ui-field__*` (общая база) и `ui-<component>__*` (хук). Хуки реально используются:
   `dropdown` → `.ui-text-field__control`, `number-input`/`textarea` → свои префиксы.
   Изначальная гипотеза «мёртвые классы» **опровергнута**.
4. **`!important`** в error-состояниях (`root.vue:339/342/433`) — костыль каскада,
   кандидат на устранение через порядок селекторов.
5. **Формат `_index.scss`** — нестандартное форматирование вложенности (`(key: val,` на
   одной строке), читается тяжело; функционально корректно (пути `g()` совпадают).

## Рекомендация (моя, т.к. выбор был «без предпочтений»)

Корень — находка №1. Всё остальное (god-file, !important) — следствие того, что
«text-field тайно и есть field». Предлагаю топик **«выделить примитив `field`»**,
безопасными шагами, каждый ревьюабельный и почти поведение-сохраняющий:

- **Ф0. Заморозить контракт.** Зафиксировать публичные классы-хуки (`ui-text-field__*`
  и т.п.), которые нельзя ломать (их читают dropdown/др.). Список — в этот отчёт.
- **Ф1. Переименовать токен-карту** `components/text-field/_index.scss` →
  `components/field/_index.scss` (префикс `m-field`), поправить `@use` в `FieldRoot`.
  Чистый перенос, поведение идентично.
- **Ф2. Вынести `mFieldProps`** из `text-field/props.ts` в общий field-модуль; обновить
  импорты у 5 потребителей. Диффы мелкие, механические.
- **Ф3. Разбить `FieldRoot`**: вычисление классов → `useFieldClasses` (composable/util);
  SCSS → партиалы (`_base/_filled/_outlined/_plain.scss`); убрать `!important` порядком.
- **Ф4.** `text-field/index.vue` остаётся тонким (это правильно), но теперь явно —
  потребитель именованного примитива `field`.

Каждый шаг = отдельный минимальный diff + прогон `npm run lint` / `lint:style` / `test`.
