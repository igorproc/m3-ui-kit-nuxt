# Оси

**Ось** — это именованное измерение вариативности, означающее одно и то же в каждом
компоненте, у которого оно есть. Словарь кита намеренно мал: одно слово — один смысл.

## Канонические юнионы

Объявлены один раз в [`shared/types/props.ts`](../../../src/runtime/shared/types/props.ts),
рантайм-определения — в
[`shared/utils/props/index.ts`](../../../src/runtime/shared/utils/props/index.ts).

| Ось | Юнион | Значит |
|---|---|---|
| `color` | `MColor` — `primary \| secondary \| tertiary \| error` | Семантическая роль, никогда не оттенок. |
| `variant` | `MVariant` — `elevated \| filled \| tonal \| outlined \| text \| plain` | Обработка поверхности: как нарисована коробка и сколько акцента она несёт. |
| `density` | **Набор значений не определён — см. ОВ-1.** | Масштаб. Единственное слово кита для «насколько крупно / насколько плотно». |
| `shape` | `MShape` — шкала скруглений MD3 | Ступень радиуса, зеркалит `$theme-shape-link`. |
| `tag` | Своя у каждого компонента | Каким элементом компонент рендерит свою обёртку. |

Оси, общие для семейства, а не для кита, живут вместе с семейством: `MFieldLabelPlacement` в
[`text-field/props.ts`](../../../src/runtime/components/ui/text-field/props.ts), раздаётся
остальным полям через `mFieldProps`.

## Правило: сужай, а не переобъявляй

Компонент, поддерживающий подмножество оси, **выводит** его:

```ts
export type MAlertVariant = Extract<MVariant, 'tonal' | 'outlined'>
export type MAvatarShape = Extract<MShape, 'full' | 'large' | 'medium' | 'small'>
```

А не пишет похожий юнион. Самостоятельная копия отлично компилируется и потом расходится: в
день, когда `MVariant` получит нового члена, копия молча его не получит, и два смысла одного
слова разъедутся без единой ошибки.

Единственное законное исключение — ось семейства, которая на самом деле является **другим**
измерением под знакомым именем: филдовый `variant` (`filled | outlined | underline`) — это
форма границы инпута, а не шкала акцента у кнопки. Берёшь исключение — напиши об этом
комментарием прямо у объявления, как сделано в `mFieldProps`.

## Правило: ось — не флаг

См. [principles.md](principles.md#в1-это-ось-или-значение). Булев проп, называющий позицию,
режим или стиль, — свёрнутое перечисление. Разверни его до релиза.

## Правило: одно слово — один смысл

| Слово | Зарезервировано за | Не за |
|---|---|---|
| `variant` | Обработка поверхности / стиль границы. | Серьёзность, назначение, стратегия поведения. |
| `color` | Семантическая роль `MColor`. | Произвольные оттенки и брендовые акценты. |
| `density` | **Масштаб во всех его видах.** У кита для этого одно слово: не `size`, не `scale`. | — |
| `shape` | Шкала скруглений. | Силуэт или раскладка. |
| `mode` | Стратегия, по которой работает компонент (`lazy`, `overlay`, `time-picker`). | Что-либо с визуальным смыслом. |
| `tag` | Элемент-обёртка, которым рендерится компонент. | Что-либо про внешний вид. |
| `type` | Не определено — см. ОВ-2. Не заводить ни на чём новом. | — |
| `<x>Placement` | Где стоит часть (`labelPlacement`). | Выравнивание внутри части. |

### Замечание о `tag`

Сегодня существуют две формы: `<MButton>` принимает семантические значения
(`button | link`) и сам разрешает их в элемент; `<MSurface>` принимает имя элемента напрямую.
Обе защитимы — семантическая форма охраняет контракт доступности кнопки, прямая удобна для
пассивного контейнера. Следуй той, что уже используется в твоём компоненте, и предпочитай
семантическую, когда выбор элемента несёт смысл.

## Как обстоит сейчас

Сужают правильно: `alert` (`variant`), `avatar` (`variant`, `shape`).

Оси семейства раздаются правильно: `mFieldProps` в `text-field`, `textarea`, `number-input`,
`autocomplete`, `file-input`.

`<MOtpInput>` **сознательно не** раздаёт `mFieldProps`, и это рассуждение стоит прочитать
прежде, чем решить, что компонент в форме поля обязан их брать: три унаследованных пропа
против четырёх, которые пришлось бы обезвредить или переопределить. Общий вид едет через
токены — см. [craft.md](craft.md).

Самостоятельные юнионы, пересекающиеся с канонической осью: `text-field`, `textarea`,
`number-input`, `dropdown`, `surface`, `banner`. Тройка полей — задокументированное
исключение выше; остальные учтены в [decisions.md](decisions.md) с ожидающими миграциями.

## Открытые вопросы

Реальные конфликты в коде. Им нужно решение, а не догадка. Пока вопрос не закрыт — следуй
локальной конвенции того компонента, в котором находишься, и не распространяй её дальше.

### ОВ-1. Набор ступеней для `density`

Слово определено: `density` — единственное имя масштаба в ките (см.
[decisions.md](decisions.md)). **Значения** — нет. Написаний три: `sm | md | lg`,
`small | medium | large`, `compact | default | comfortable`, — и выбор между ними не
является вопросом наименования.

Размеры в ките резиновые: `root-scale()` пересчитывает корневой размер шрифта по брейкпойнту,
поэтому каждый `rem` уже едет вместе с вьюпортом. Фиксированная лестница из трёх ступеней
поверх этого может оказаться неверной формой вообще — честный ответ должен прийти из
реального потребления: к каким ступеням продукты действительно тянутся и где резиновая шкала
уже закрывает потребность. Решать по данным использования, а не по вкусу.

### ОВ-2. `type` означает две разные вещи

Нативный проброс (`MButtonType`, `MTextFieldType`) и таксономия компонента (`MChipType`,
`MAlertType`, `MLoadingType`, `MToolbarType`, `MAppBarType`) делят одно слово. Хуже того,
`MAlertType = info | success | warning | error` — это **семантическая роль цвета** под именем
`type`, то есть ровно то, для чего у кита уже есть каноническая ось.

Оставлено открытым сознательно: `type` в каждом месте действительно несёт разный смысл, и
резервирование сейчас потребовало бы переименования до того, как станет ясно правильное
разделение. Не вводи `type` ни на чём новом, пока вопрос не закрыт.
